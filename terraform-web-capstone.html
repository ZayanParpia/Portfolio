What I Built

I built a secure AWS web infrastructure using Terraform (IaC), bringing together Amazon VPC, public and private subnets, multiple Availability Zones, Internet and NAT Gateways, AWS WAF, an Application Load Balancer, EC2 with Auto Scaling, Systems Manager Session Manager, Security Groups, Network ACLs, IAM, KMS, private S3, CloudWatch, VPC Flow Logs, Linux, Docker, CI/CD, and GitHub.

How It Works

Public traffic passes through AWS WAF and the Application Load Balancer to web servers in private subnets across multiple Availability Zones. Auto Scaling adjusts capacity as workload changes, while the NAT Gateway provides controlled outbound access. SSM Session Manager avoids public SSH access; least-privilege IAM, KMS encryption, private S3, CloudWatch, and VPC Flow Logs provide security and operational visibility. Docker packages the application, and Terraform with CI/CD supports repeatable infrastructure changes.

Traffic and Operations Flow

Internet -> AWS WAF -> Application Load Balancer -> Private EC2
Admin -> SSM Session Manager -> Private EC2
Private EC2 -> NAT Gateway -> Internet
AWS Resources -> CloudWatch / VPC Flow Logs -> Private S3

Inbound vs. Outbound Traffic

Inbound:
Internet -> WAF -> ALB -> Private EC2

Outbound (from EC2):
Private EC2 -> NAT Gateway -> Internet Gateway -> Internet

Only the required web traffic reaches the application path; outbound access lets private instances reach external resources without becoming public-facing.

CI/CD Pipeline

GitHub -> CI/CD
  - Format / Validate
  - Terraform checks
  - Terraform Plan
  - Deployment workflow -> AWS

Automating these checks connects the infrastructure to a real development workflow rather than a one-time script.

Security Design for Defense in Depth

This project was intentionally designed around defense in depth rather than relying on a single security control.

  1. Web application protection: AWS WAF sits in front of the ALB and inspects incoming traffic. Future testing will validate it against directory traversal, injection-style requests, suspicious URL patterns, and controlled high-volume request simulations. Attack simulations are planned and have not been simulated yet.
  2. Network segmentation: EC2 web servers live in private subnets across multiple Availability Zones, limiting exposure while adding redundancy.
  3. No SSH exposure: Administration goes through AWS Systems Manager Session Manager instead of opening port 22.
  4. Least-privilege IAM: IAM roles and policies grant users and services only the permissions required for their job (PoLP).
  5. Storage protection: S3 is configured as private storage with Block Public Access enabled; data at rest is protected with AWS KMS.
  6. Network visibility: VPC Flow Logs provide visibility into network communication and evidence for troubleshooting and security investigation.

Planned Security Validation

The infrastructure screenshots and video demonstration document the deployed environment. Controlled security testing to validate the WAF and monitoring pipeline, including the full lifecycle of Attack → Detection/Filtering → Logging → Investigation, is still planned and has not yet been completed.

Availability & Scaling

The architecture spans multiple Availability Zones so the application doesn't depend on a single EC2 instance, subnet, or AZ. Auto Scaling adjusts EC2 capacity based on workload, and mock CPU-usage testing was used to demonstrate how increased resource utilization triggers scaling behavior — hands-on experience with the chain from Availability Zones to redundancy, load balancing, and Auto Scaling.

Monitoring & Logging

The environment was designed so security and operational events can be observed rather than assuming infrastructure "just works":

  • VPC Flow Logs — network visibility and traffic investigation.
  • CloudWatch — EC2 CPU utilization, resource behavior, alarms, and operational visibility.
  • S3 — durable destination for stored logs and data.

Deployment & Application Delivery

Terraform makes the environment reproducible through a plan-and-apply workflow (init → fmt → validate → plan → apply), instead of clicking through the AWS Console. A CI/CD pipeline automates formatting, validation, Terraform checks, and the deployment workflow on every change, connecting the infrastructure work to a real development workflow rather than a one-time script. Docker packages the application so its runtime stays consistent and reproducible on EC2.
